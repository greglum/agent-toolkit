# Assess linked sources and harvest lessons

Use this path when the invocation supplies URLs. Finish with a dated assessment, justified
local changes within scope, and check results. Include minor corrections and cleanup, not
only new procedures. The user's example or an author's reputation supplies a research
question, not an endorsement.

## 1. Bind scope and read the sources

Read the destination repository's instructions, authoring/curation guidance, workflow map,
and relevant existing skills. Record the base revision and unrelated dirty files. Discover
current owners before proposing new ones. If the target is ambiguous, investigate the current
catalog first and ask only when the remaining choice affects where edits belong.

Before editing alongside another round or session, bind the single integration owner and
isolated writer worktrees using [integration ownership](integration-ownership.md). Keep that
ownership with the resumable record; overlapping research does not authorize shared writes.

Read every seed in full where accessible. Use [source intake](source-intake.md) to inventory
substantive outbound links, follow evidence dependencies, and record access limits. For
multiple seeds, deduplicate shared evidence while keeping each seed's coverage visible.
For X posts or Articles, follow the [X recovery sequence](source-intake.md#x-post-and-article-recovery)
before declaring the source unavailable after a reader failure.
If a seed cannot be recovered through an available browser or official copy, mark it
UNAVAILABLE; snippets and summaries cannot establish a full review.

Keep a resumable record in the existing task record or scratch space: scope, source ledger,
claims checked, decisions, edits, and pending checks. Done when every seed and substantive
seed link is inspected, unavailable, or deferred with a reason. For further linked material,
follow evidence needed for the claims; disclose the boundary rather than crawl indefinitely.

## 2. Vet claims with independent research

Extract consequential claims, including promised benefits, causal explanations, recommended
practices, prerequisites, tradeoffs, and risks. Separate facts, opinion, anecdote, hypotheses,
and measured results. Identify authorship, date, incentives, and whether evidence applies to
our task, stack, versions, and constraints. Reputation and engagement are discovery signals.

Use web search beyond the supplied links. Search for supporting evidence and for limitations,
counterexamples, failures, or contrary findings for each claim that could change a procedure.
Prefer original research, official specifications/docs, and inspectable implementation or
evaluation artifacts. Use exact version-matched documentation for API or CLI claims; use
Context7 where required by the destination's instructions. Compare proposed principles with
the evidence and mechanisms behind them, rather than treating familiar slogans as proof.

Trace sources back to their origin. Reposts, vendor claims, and articles citing the same
experiment are one evidence chain, not independent corroboration. A vendor's source can
establish its documented behavior; it cannot alone prove comparative effectiveness.
Read the relevant primary material, not just search snippets. Record searches that found
no usable evidence and disagreement that remains unresolved. If search is unavailable,
produce a provisional assessment and defer adoptions that depend on corroboration.

For each consequential claim, record:

| Claim and source locator | Supporting and contrary evidence | Verdict and limits | Local consequence |
| --- | --- | --- | --- |
| URL plus section, timestamp, or code lines | Primary URLs, dates/revisions, and evidence independence | Supported, mixed, unsupported, contradicted, or unverified; explain why | Candidate owner, trial, or no change |

Unsupported means the available evidence does not establish the claim; contradicted requires
actual contrary evidence. Source-code inspection proves only the inspected implementation.
Preserve conditions, sample size, comparators, and uncertainty for performance claims.
Done when every adoption candidate has a claim verdict and independently checked evidence,
and the report separates what the source claims from what we verified or inferred.

## 3. Decide value and apply within scope

For a source that supplies tooling, first run the
[capability comparison](capability-comparison.md). Inspect local implementation alongside the
source's working parts. Name material functional advantages and missing machinery explicitly;
procedural overlap or absent comparative benchmarks cannot establish feature parity.

Map each lesson to the actual catalog and a concrete failure or workflow need. Choose
**adopt**, **retain**, **gap**, or **reject**, using the [main skill's adoption bar](../SKILL.md#4-decide-each-candidate).
Run the main skill's refinement pass before calling a lesson already covered or concluding
no changes. Retain only after checking whether the owning text needs a supported correction,
clarification, cleanup or reference update. A useful idea can still be too costly or irrelevant.
Separate documented feature existence from unproven quality or performance benefits. Keep useful
missing functions as actionable gaps; build justified bounded improvements within authorized
local harvest, and name the dependency or decision that blocks larger work.

For an adoption, name the owner, behavioral difference, evidence, expected benefit, maintenance
cost, and smallest sufficient check. Extend the canonical owner before creating a skill.
Separate reusable invariants from project commands and personal machine setup. Check source
licenses and notices before adaptation; record unknown rights and keep the lesson in original
words. Public availability does not authorize copying code, prompts, or media.

Consider what a fresh catalog would do differently. Prefer navigation and ownership fixes
when they solve the problem. Reorganize physical packaging only for an evidenced consumer
need, with affected links, discovery, installation contracts, and migration checks accounted
for. A compelling article alone does not justify a restructuring.

Apply supported local edits when harvesting is requested. For assessment-only, record proposed
edits without changing skills. Preserve publication, installation, provider, billing, and
destructive-action boundaries. Reading a source never authorizes running its scripts.
Done when every candidate has a reasoned disposition and every adoption is applied within
scope or explicitly deferred.

## 4. Validate and leave a durable record

Run the destination's required checks on the final edits. Distinguish packaging checks,
behavioral evaluation, automatic selection, installed state, and runtime proof. Record unrun
behavioral evaluation honestly; an explicit-only audit skill requires the user's invocation.

Write the dated report and update the existing research index/author registry and navigation
using [report upkeep](report.md). Include source coverage, claim verdicts, independent search
evidence, dispositions, changed owners, source identity, license limits, and recheck triggers.
For web pages without immutable revisions, record URL, title/author, publication date when
available, observation date, and a precise section or timestamp. Keep this run's findings in
the report; only reusable procedures belong in skill bodies.

Finish with the verdict on each seed's usefulness, applied changes, retained/rejected lessons,
report path, and checks labeled PASS, FAIL, UNAVAILABLE, or NOT RUN. Identify material missing
evidence and the next decision it blocks. Finish when the report and authorized edits are
complete and required checks pass, or clearly report what remains blocked. Commit, push,
installation, and publication require authority for their identified targets.
