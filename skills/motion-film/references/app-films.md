# Application film setup

Use this for a new application film, a refresh of its product claims, or scenes that use
environment data. Keep the brief in the project's film source folder or existing documentation
owner. Reuse the current brief and storyboard rather than making parallel records.

## New films and source refreshes

- Record the app revision and observation date, audience, intended task, supported viewing
  surface, delivery format and runtime budget, design owners, permitted assets/data, audio
  scope, and actual check/capture/export commands. Keep credentials and private voice
  identifiers out of the brief.
- Ground journeys in routes, UI labels, permissions, feature flags, and current behavior.
  Keep a consistent fictional cast when examples are permitted. A source-backed feature
  that the intended viewer cannot access does not establish a usable journey for them.
- Use a project-owned film template or installed renderer when it fits. With neither, build
  the smallest time-driven scene surface and capture/export path that meet the brief. Keep
  standalone film files separate from application runtime code. This skill bundles no engine;
  dependency additions and application integration follow the repository's own gates.
- For an update, compare the brief's recorded revision with the affected source paths. Record
  scene, previous claim, current behavior, evidence, and the required change. Respect pending
  product changes that the final film depends on; regenerate against the completed source.
  Preserve opening, replay, and per-film version policy when working on an existing series.

## Environment data and editing previews

- Follow the owner's data policy. Use fictional examples when permitted and label them on
  screen and in the accessible text. If the brief requires environment data, a sample-data
  fallback does not complete it. Confirm the read scope and whether those records may appear
  in an exported or shared artifact; access to an embedded player alone does not grant that use.
- Prepare required reads through the existing permission-checked services and parsers. Freeze
  the selected inputs for that showing or render. A scene starts when its reads succeed;
  the opening's duration is not a readiness signal. Keep loading, failure/retry, and successful
  empty states distinct. Check delayed reads and failure recovery in the closest existing rig.
- When depicting search, paint results returned for the displayed query. A limited story pool
  cannot establish that the environment has no matches. Preserve the real wire format through
  parsing, including dates represented as strings.
- Demonstrate editing in a local copy, visibly marked as an unsaved preview when it could be
  mistaken for a real change. Keep saved records intact; the film does not submit mutations.

Reference imagery can guide composition and hierarchy. Moving evidence with source timestamps
is needed to support claims about pacing, easing, or sound timing. Apply only the mechanisms
that fit the app's visual language and the requested story.
